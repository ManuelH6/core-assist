# WORKFLOW COMPLET DE CORE ASSIST

```text

COMPRÉHENSION DU BESOIN
       │
       ▼
ÉTUDE ET CADRAGE DE LA DEMANDE
       │
       ▼
DÉCISION DE DONNER SUITE
       │
       ▼
PRÉPARATION DE LA MISSION
       │
       ▼
AFFECTATION DE L'ÉQUIPE
       │
       ▼

       │
       ▼

       │
       ▼

       │
       ▼
```

Ce parcours est la trame générale. Certaines activités se déroulent en même temps. D'autres peuvent être reprises ou corrigées.

## 2. Réception d'une demande client

**Objectif : comprendre ce que le client demande avant de décider de lui proposer une mission.**

### Étape 2.1 - Le client fait une demande

La demande peut être enregistrée par :
- un manager ;
- le DG ;
- un autre collaborateur autorisé ;
- éventuellement le client, si un formulaire externe est prévu.

Le système enregistre notamment :
- le nom du client ;
- la personne qui fait la demande ;
- la date de réception ;
- le sujet de la demande ;
- les explications fournies ;
- les documents éventuellement transmis.

### Étape 2.2 - Création de la fiche de compréhension initiale

Dès qu'une demande est enregistrée, Core Assist crée systématiquement une fiche de compréhension initiale.

Cette fiche sert à répondre à quelques questions :

- Qui est le client ?
- Quel est son besoin ?
- Quel problème cherche-t-il à résoudre ?
- Quel résultat espère-t-il obtenir ?
- Quel est le contexte ?
- Quelles informations manquent encore ?

Le responsable de la demande complète et corrige la fiche.

### Étape 2.3 - Examen de la demande

Le DG ou le manager examine les informations disponibles.

Il peut :
- demander des précisions ;
- demander des documents complémentaires ;
- échanger avec le client ;
- poursuivre l'étude de la demande ;
- décider de ne pas donner suite.

**Conséquence dans le système :** la demande avance avec son état réel. Les informations et les échanges sont conservés.

### Étape 2.4 - Décision de donner suite

Si le cabinet décide de poursuivre, il prépare une proposition commerciale.

Attention : la proposition commerciale, la négociation et la signature du contrat ne sont pas nécessairement gérées dans Core Assist. Nous avons déjà décidé que le contrat externe reste hors de l'application.

Lorsque l'accord du client est obtenu, le cabinet peut passer à la préparation de la mission.

Si la demande n'aboutit pas, elle reste enregistrée avec son résultat. Elle ne doit pas disparaître.

---

## 3. Création et préparation de la mission

**Objectif : transformer une demande acceptée en mission de travail pour le cabinet.**

### Étape 3.1 - Création de la mission

Le DG ou le manager crée une mission à partir de la demande acceptée.

Core Assist récupère les informations déjà enregistrées :
- le client ;
- le besoin ;
- le contexte ;
- les objectifs initiaux ;
- les résultats attendus ;
- les conditions déjà convenues.

On évite ainsi de demander à l'utilisateur de saisir une deuxième fois les mêmes informations.

Une demande peut donner lieu à plusieurs missions. Il faut donc conserver le lien entre la demande initiale et chaque mission créée.

### Étape 3.2 - Préparation de la Mission Framing Sheet™ (MFS)

Le DG ou le manager ouvre la fiche de cadrage de la mission.

Il complète notamment :
- le titre de la mission ;
- son objectif précis ;
- les résultats attendus ;
- les limites de l'intervention ;
- les contraintes ;
- les dates prévues ;
- les conditions particulières ;
- le responsable de la mission.

Il peut aussi corriger certaines informations héritées de la demande, mais Core Assist doit conserver leur origine et les modifications apportées.

### Étape 3.3 - Validation du cadrage opérationnel

Le cadrage est examiné et validé par la personne habilitée.

Une fois validé, il devient la référence pour préparer le travail.

**Conséquences :**
- les autres outils peuvent récupérer les informations de la mission ;
- le périmètre du diagnostic peut être préparé ;
- les travaux peuvent être organisés ;
- les informations de référence sont conservées.

Le cadrage peut être modifié par la suite si la mission évolue. Il faut alors conserver les anciennes versions.

---

## 4. Constitution de l'équipe

**Objectif : savoir qui va travailler sur la mission et dans quel rôle.**

Le DG ou le manager choisit les collaborateurs qui participeront à la mission.

Il peut désigner :
- un chef de mission ;
- un ou plusieurs consultants ;
- des experts ;
- un responsable ou manager de suivi.

Une même personne peut avoir plusieurs rôles.

### Ce que fait Core Assist

Le système :
1. Enregistre les membres de la mission.
2. Enregistre leur rôle dans cette mission.
3. Leur donne accès aux informations autorisées.
4. Permet de leur attribuer des travaux.
5. Conserve les dates et les changements d'affectation.

L'équipe peut être modifiée en cours de mission.

Une personne retirée de la mission ne doit cependant pas faire disparaître les travaux qu'elle a déjà réalisés.

---

## 5. Préparation du diagnostic

C'est ici que les outils du Diagnostic 360° commencent à jouer leur rôle principal.

### Étape 5.1 - Définition du périmètre avec le DSC

Le responsable ouvre le Diagnostic Scope Canvas™ (DSC).

Il définit ce que le cabinet va examiner.

Par exemple, pour une entreprise :

| Domaine | Éléments possibles |
|---|---|
| Organisation | Structure, responsabilités, fonctionnement |
| Finances | Trésorerie, dépenses, recettes |
| Ressources humaines | Effectifs, compétences, organisation |
| Commercial | Clients, ventes, concurrence |
| Opérations | Production, qualité, délais |

Pour chaque élément, il précise s'il est :
- inclus dans le diagnostic ;
- exclu ;
- à confirmer.

Il peut également préciser la profondeur de l'examen.

Un domaine peut être retenu sans que tous ses éléments le soient.

### Étape 5.2 - Enregistrement du périmètre

Lorsque le périmètre est validé, Core Assist enregistre sa version.

C'est important : si le périmètre change plus tard, les anciennes analyses doivent rester liées au périmètre qui existait au moment où elles ont été réalisées.

### Étape 5.3 - Préparation du DIR

Le responsable ouvre le Diagnostic Intake Register™ (DIR).

Il définit les informations qu'il faut obtenir pour examiner les éléments retenus.

Exemple :

| Élément à examiner | Information recherchée | Source attendue |
|---|---|---|
| Trésorerie | État de la trésorerie | Documents financiers |
| Ventes | Évolution des ventes | Registre des ventes |
| Ressources humaines | Nombre de salariés | Liste du personnel |
| Organisation | Répartition des responsabilités | Organigramme |

Pour chaque information, il peut préciser :
- pourquoi elle est nécessaire ;
- comment l'obtenir ;
- qui doit la rechercher ;
- sa priorité ;
- son état d'avancement.

Core Assist peut proposer une première liste à partir du périmètre. Le responsable la vérifie et la complète.

### Étape 5.4 - Préparation du SIG

En parallèle, le responsable ouvre le Stakeholder Input Grid™ (SIG).

Il identifie les personnes ou groupes qui peuvent apporter des informations utiles.

Par exemple :
- le directeur général ;
- le responsable financier ;
- les responsables de services ;
- les employés ;
- certains clients ;
- des partenaires.

Pour chacun, il précise :
- son rôle dans l'organisation ;
- les informations ou contributions attendues ;
- la manière de le contacter ;
- la personne chargée de le rencontrer ;
- l'état de la prise de contact.

**Différence entre DIR et SIG :**

- DIR : quelles informations devons-nous obtenir ?
- SIG : auprès de qui pouvons-nous obtenir des informations utiles ?

Les deux outils avancent en parallèle.

### Étape 5.5 - Organisation des travaux

Le responsable organise les investigations dans Core Assist.

Il peut créer des travaux :
- par domaine ;
- par axe ;
- par groupe d'informations ;
- par activité ;
- ou de manière transversale.

Il affecte un ou plusieurs collaborateurs à chaque travail.

Un consultant peut participer à plusieurs travaux. Plusieurs consultants peuvent également travailler sur un même axe.

Le système enregistre :
- le travail à réaliser ;
- son responsable ;
- ses participants ;
- les personnes chargées de le vérifier ;
- ses délais ;
- son état d'avancement.

Il n'est pas nécessaire de créer un travail pour chaque petite action. Il faut que les travaux correspondent à une véritable organisation du travail de l'équipe.

---

## 6. Réalisation des investigations

**Objectif : recueillir les informations nécessaires au diagnostic.**

C'est une phase où plusieurs personnes peuvent travailler simultanément.

### Étape 6.1 - Le consultant ouvre son travail

Le consultant consulte les travaux qui lui sont attribués.

Il voit notamment :
- les objectifs du travail ;
- les informations à rechercher ;
- les personnes à rencontrer ;
- les documents attendus ;
- les consignes ;
- les échéances.

Il peut consulter les informations déjà recueillies par les autres membres de l'équipe, selon ses droits.

### Étape 6.2 - Collecte des informations

Le consultant peut :
- recevoir un document ;
- réaliser un entretien ;
- observer une situation ;
- consulter une base de données ;
- relever un chiffre ;
- recueillir une déclaration ;
- enregistrer une autre information utile.

Chaque élément recueilli est enregistré dans la collecte commune.

Par exemple, un document financier reçu ne doit pas être copié séparément dans le DIR, le SIG et le D360.

Il est enregistré une fois, puis relié aux besoins et contributions concernés.

### Étape 6.3 - Mise à jour du DIR et du SIG

Lorsqu'un élément est reçu :

- le DIR permet de dire à quel besoin d'information il répond ;
- le SIG permet de dire à quelle contribution attendue il correspond.

Le système met à jour les états de collecte concernés.

Mais attention : recevoir un document ne signifie pas que l'information est correcte.

La collecte et la vérification sont deux choses différentes.

### Étape 6.4 - Vérification des informations

Le consultant ou la personne responsable examine les informations recueillies.

Il peut constater :
- que l'information est exploitable ;
- qu'elle est incomplète ;
- qu'elle doit être confirmée ;
- qu'elle contredit une autre source ;
- qu'elle n'est pas pertinente.

Il faut conserver ces observations. Une information contradictoire ne doit pas être supprimée simplement parce qu'une autre source semble plus convaincante.

### Étape 6.5 - Enregistrement du travail

Le consultant peut sauvegarder son travail autant de fois qu'il le souhaite.

Il peut notamment enregistrer :
- ses observations ;
- ses notes ;
- les informations obtenues ;
- les difficultés rencontrées ;
- les éléments qui restent à rechercher.

Il n'est pas obligé de soumettre son travail dès qu'il le sauvegarde.

### Étape 6.6 - Soumission du travail

Lorsque le consultant estime son travail prêt, il le soumet.

À ce moment :
- Core Assist conserve la version soumise ;
- le travail passe dans l'état correspondant à la soumission ;
- le chef de mission peut examiner le travail ;
- les personnes autorisées sont informées selon les règles de notification.

Le DG peut consulter les travaux soumis et les informations auxquelles il a accès. Il ne doit pas voir comme soumis un travail que le consultant a seulement sauvegardé sans le transmettre.

### Étape 6.7 - Examen du travail

Le chef de mission examine le travail.

Il peut :
- l'accepter ;
- demander des corrections ;
- demander des informations supplémentaires ;
- signaler un problème ;
- demander un complément.

S'il demande un complément, le consultant peut reprendre le travail concerné sans qu'il soit nécessaire de créer systématiquement un nouveau travail.

La demande et la réponse doivent rester visibles dans l'historique.

**Point important :** une demande de complément ne signifie pas automatiquement que le périmètre de la mission change.

Si le travail révèle qu'il faut examiner un élément supplémentaire, le périmètre doit être modifié séparément.

---

## 7. Analyse des informations avec le D360

Les investigations ne doivent pas nécessairement être terminées pour commencer l'analyse.

Dès que des informations suffisantes sont disponibles sur un sujet, le consultant peut commencer à l'examiner.

### Étape 7.1 - Ouverture de la matrice D360

Le consultant ouvre la 360° Diagnostic Matrix™.

Core Assist lui présente les éléments du périmètre qui doivent être examinés.

Il peut retrouver :
- les informations du MFS ;
- le périmètre défini dans le DSC ;
- les besoins du DIR ;
- les contributions du SIG ;
- les éléments recueillis ;
- les travaux déjà soumis.

### Étape 7.2 - Analyse d'un élément

Pour chaque élément examiné, le consultant décrit :

1. Ce qui est réellement observé.
2. Ce qui fonctionne bien.
3. Ce qui fonctionne mal ou pose problème.
4. Les causes possibles.
5. Les conséquences éventuelles.
6. Les informations qui manquent.
7. Les éléments qui permettent de soutenir son analyse.

Exemple :

**Élément examiné : gestion de la trésorerie.**

- Observation : l'entreprise ne dispose pas d'un suivi régulier de sa trésorerie.
- Point positif : les recettes et les dépenses sont enregistrées.
- Difficulté : aucune prévision de trésorerie n'est établie.
- Cause possible : absence de procédure de suivi.
- Conséquence possible : difficultés à anticiper les périodes de manque de liquidités.
- Sources : documents financiers et entretien avec le responsable financier.

### Étape 7.3 - Association des sources

Le consultant associe les informations recueillies à son analyse.

Une même source peut être utilisée dans plusieurs analyses.

Une analyse peut également s'appuyer sur plusieurs sources.

Il doit pouvoir préciser ce que chaque source permet de confirmer et quelles sont ses limites.

### Étape 7.4 - Synthèse des résultats

Le D360 permet de regrouper les résultats par axe et par domaine.

On doit pouvoir retrouver :
- les points forts ;
- les difficultés ;
- les constats ;
- les informations insuffisantes ;
- les contradictions ;
- les sujets qui nécessitent encore des investigations.

Le système ne doit pas inventer une note ou une appréciation automatique si le cabinet n'a pas défini de méthode de notation.

### Étape 7.5 - Mise à jour progressive

L'analyse peut évoluer au fur et à mesure que de nouvelles informations arrivent.

Par exemple :

Un consultant analyse la trésorerie à partir de trois documents. Quelques jours plus tard, un quatrième document révèle une contradiction.

Core Assist doit permettre de :
- retrouver l'analyse concernée ;
- identifier la nouvelle source ;
- signaler que l'analyse mérite d'être réexaminée ;
- conserver la version précédente ;
- enregistrer la nouvelle analyse.

Il ne doit pas modifier silencieusement une analyse déjà soumise ou utilisée dans un rapport.

---

## 8. Identification et organisation des problèmes avec le PSG

Le D360 permet de comprendre la situation. Le PSG permet d'aller plus loin en organisant les problèmes identifiés.

### Étape 8.1 - Sélection d'un constat

Le consultant ouvre le Problem Structuring Grid™.

Il sélectionne un constat issu du D360 qu'il souhaite examiner plus profondément.

Tous les constats ne deviennent pas nécessairement des problèmes.

Un constat peut simplement être une force, une observation ou une information à approfondir.

### Étape 8.2 - Création d'un problème

Pour chaque problème retenu, il précise :
- son titre ;
- sa description ;
- le domaine concerné ;
- le constat dont il provient ;
- ses manifestations ;
- son état d'analyse.

Un problème peut provenir de plusieurs constats. Un constat peut également contribuer à identifier plusieurs problèmes.

### Étape 8.3 - Recherche des causes

Le consultant cherche à comprendre pourquoi le problème existe.

Il peut identifier plusieurs causes.

Il doit distinguer :
- une cause simplement supposée ;
- une cause partiellement confirmée ;
- une cause suffisamment confirmée.

Il faut éviter de présenter une hypothèse comme un fait établi.

### Étape 8.4 - Identification des conséquences

Le consultant décrit les effets du problème sur l'organisation.

Par exemple :
- pertes financières ;
- retards ;
- baisse de qualité ;
- insatisfaction des clients ;
- mauvaise répartition du travail.

### Étape 8.5 - Relations entre les problèmes

Plusieurs problèmes peuvent être liés.

Exemple :

```text
Mauvaise répartition des responsabilités
                  │
                  ▼
        Retards dans les décisions
                  │
                  ▼
       Retards dans les opérations
                  │
                  ▼
       Insatisfaction des clients
```

Le PSG permet de représenter ces relations.

Cela évite de traiter chaque difficulté comme si elle était indépendante des autres.

### Étape 8.6 - Priorisation des problèmes

Le consultant examine l'importance de chaque problème.

Il peut prendre en compte :
- sa gravité ;
- sa fréquence ;
- le nombre de personnes concernées ;
- son urgence ;
- ses conséquences sur les objectifs de l'entreprise.

Le système présente les critères retenus par le cabinet. Il ne doit pas inventer une formule de calcul qui n'a pas été définie.

Les problèmes peuvent ensuite être classés par ordre de priorité.

---

## 9. Préparation du rapport avec le DRD

**Objectif : transformer les résultats du diagnostic en un document clair que le client peut comprendre.**

Le Diagnostic Restitution Deck™ sert à préparer le rapport formel de la mission.

### Étape 9.1 - Création du rapport

Le consultant ouvre le DRD.

Core Assist peut lui proposer une première structure à partir des informations disponibles :

1. Présentation de la mission.
2. Objectifs du diagnostic.
3. Méthode utilisée.
4. Périmètre examiné.
5. Résumé général.
6. Analyse des différents domaines.
7. Forces de l'organisation.
8. Difficultés identifiées.
9. Problèmes prioritaires.
10. Conclusion.

Cette structure peut être modifiée.

### Étape 9.2 - Ajout des résultats

Le consultant peut insérer dans le rapport :
- des textes ;
- des tableaux ;
- des graphiques ;
- des résultats du D360 ;
- des problèmes du PSG ;
- des recommandations ;
- des conclusions personnelles.

Il peut également rédiger des commentaires complémentaires.

Lorsqu'il importe un résultat du D360 ou du PSG, Core Assist conserve le lien avec sa source.

Le rapport ne doit pas recopier aveuglément toutes les données des autres outils.

### Étape 9.3 - Vérification du périmètre réellement examiné

Le rapport doit distinguer :

- ce qui était prévu dans le diagnostic ;
- ce qui a effectivement été examiné ;
- ce qui n'a été examiné que partiellement ;
- ce qui n'a pas été examiné ;
- les raisons de ces limites.

C'est essentiel pour que le client comprenne exactement la portée du diagnostic.

### Étape 9.4 - Préparation d'une version

Le consultant enregistre une version du rapport.

Cette version peut être examinée par le chef de mission ou par le responsable habilité.

Il peut demander :
- des corrections ;
- des précisions ;
- une meilleure présentation ;
- des justifications supplémentaires ;
- une révision de certaines conclusions.

Le consultant peut ensuite soumettre une nouvelle version.

Les versions précédentes restent conservées.

---

## 10. Examen du rapport par le client

Le rapport est transmis au client depuis son espace dans Core Assist.

### Étape 10.1 - Le client consulte le rapport

Le client peut :
- consulter le rapport ;
- télécharger le document si cette possibilité est prévue ;
- faire des commentaires ;
- signaler des erreurs ;
- demander des précisions ;
- valider le rapport.

### Étape 10.2 - Le client formule des observations

Si le client demande des corrections, Core Assist transmet ses observations aux personnes concernées.

Le cabinet examine chaque demande.

Il peut :
- accepter la correction ;
- apporter une précision ;
- expliquer pourquoi il ne retient pas une observation ;
- demander un échange complémentaire.

Le consultant prépare ensuite une nouvelle version si nécessaire.

### Étape 10.3 - Validation du rapport

Lorsque le client est satisfait, il peut valider le rapport.

Core Assist conserve :
- la version validée ;
- la date de validation ;
- l'identité de la personne qui a validé ;
- les éventuelles observations associées.

**La validation du rapport ne signifie pas automatiquement que la mission est terminée.**

C'est une distinction que nous avons déjà retenue.

---

## 11. Préparation des actions avec le NSR

Le Next-Step Router™ intervient pour transformer les résultats du diagnostic en propositions concrètes.

### Étape 11.1 - Création des recommandations

Le consultant examine les résultats du D360 et du PSG.

Il formule des recommandations pour améliorer la situation de l'organisation.

Une recommandation explique ce qu'il serait souhaitable de faire et pourquoi.

Exemple :

> Mettre en place un suivi mensuel de la trésorerie afin de mieux anticiper les besoins de financement.

Chaque recommandation peut être liée à un ou plusieurs problèmes.

### Étape 11.2 - Définition des actions

Une recommandation peut être transformée en une ou plusieurs actions.

Exemple :

**Recommandation :** mettre en place un suivi mensuel de la trésorerie.

Actions possibles :
1. Définir un modèle de suivi.
2. Désigner un responsable.
3. Former la personne chargée du suivi.
4. Mettre en place un calendrier mensuel.
5. Examiner les premiers résultats.

Pour chaque action, le consultant peut préciser :
- le résultat attendu ;
- le responsable proposé ;
- les personnes concernées ;
- les moyens nécessaires ;
- les délais indicatifs ;
- les dépendances avec d'autres actions ;
- le niveau de priorité.

### Étape 11.3 - Prise en compte des décisions et engagements

Le NSR peut récupérer les engagements enregistrés dans le Live Decision Capture.

Exemple :

Pendant une réunion, le directeur financier s'est engagé à transmettre un document avant une date donnée.

Cet engagement peut être repris dans le NSR.

Mais il faut conserver la différence entre les deux :

- LDC : ce qui a été décidé ou promis pendant un échange.
- NSR : ce qui est proposé comme action à réaliser dans la suite du travail.

Un engagement ne devient pas automatiquement une action validée.

### Étape 11.4 - Présentation des prochaines étapes

Le consultant organise les actions selon :
- leur priorité ;
- leur ordre d'exécution ;
- leurs dépendances ;
- les délais ;
- les moyens nécessaires.

Le client peut examiner ces propositions.

Il peut accepter certaines actions, en refuser d'autres ou demander des modifications.

Une action proposée ne doit pas être considérée comme acceptée tant que la décision correspondante n'a pas été enregistrée.

### Étape 11.5 - Suivi des actions

Si le cabinet accompagne ensuite le client dans la mise en œuvre, les actions peuvent faire l'objet d'un suivi.

Il faudra cependant distinguer le suivi des actions du diagnostic lui-même.

Le NSR ne doit pas devenir à lui seul un logiciel complet de gestion de projets.

---

## 12. Utilisation du LDC pendant toute la mission

Le Live Decision Capture ne constitue pas une étape qui arrive après les autres.

Il est disponible tout au long de la mission.

À chaque réunion ou échange important, un utilisateur autorisé peut créer un enregistrement.

Il peut préciser :
- la date ;
- les participants ;
- le sujet ;
- les points discutés ;
- les décisions prises ;
- les personnes responsables ;
- les engagements ;
- les échéances.

Exemple :

Une réunion est organisée pour discuter des difficultés financières de l'entreprise.

Pendant la réunion :
- un point concerne les retards de paiement ;
- une décision est prise pour examiner les créances anciennes ;
- le responsable financier s'engage à transmettre un état des créances avant vendredi.

Le système conserve ces informations et leurs liens avec les sujets concernés.

Il faut également pouvoir modifier une décision si elle est révisée ou annulée, sans effacer son historique.

Le LDC sert donc à conserver la mémoire des échanges et des décisions de la mission.

---

## 13. Alimentation du DAP pendant toute la mission

Le Diagnostic Archive Pack ne doit pas attendre la fin de la mission pour être créé.

Il se construit progressivement.

Il référence notamment :
- les informations de cadrage ;
- les différentes versions du périmètre ;
- les documents reçus ;
- les éléments recueillis ;
- les résultats des analyses ;
- les problèmes identifiés ;
- les décisions ;
- les rapports ;
- les versions validées ;
- les recommandations ;
- les actions proposées.

Son rôle est de permettre de retrouver facilement ce qui a été fait, quand, par qui et à partir de quelles informations.

Il ne doit pas créer une deuxième copie de tous les documents et de tous les résultats.

Il doit conserver des références vers les éléments déjà enregistrés dans Core Assist.

---

## 14. Clôture de la mission

La clôture intervient lorsque le cabinet estime que les travaux prévus sont terminés.

### Étape 14.1 - Vérification avant clôture

Le responsable de la mission vérifie notamment :

- Les travaux prévus ont-ils été réalisés ou leur état final est-il justifié ?
- Les travaux soumis ont-ils été examinés ?
- Le rapport formel a-t-il été produit ?
- Le client a-t-il reçu le rapport ?
- Les observations du client ont-elles été traitées ?
- Les décisions importantes ont-elles été enregistrées ?
- Les prochaines étapes ont-elles été préparées ?
- Les documents et résultats importants sont-ils retrouvables ?

Tous les travaux ne doivent pas nécessairement être considérés comme terminés de la même manière. Certains peuvent être abandonnés, reportés ou non réalisés avec une justification.

### Étape 14.2 - Demande de clôture

Le responsable demande la clôture de la mission.

La personne habilitée examine la demande et peut :
- accepter la clôture ;
- demander des éléments complémentaires ;
- refuser temporairement la clôture.

### Étape 14.3 - Clôture effective

Lorsque la clôture est autorisée :

- la mission passe à l'état clôturé ;
- les travaux sont conservés ;
- les outils et leurs versions restent consultables ;
- le rapport validé reste accessible ;
- le DAP conserve l'inventaire des éléments de la mission ;
- les historiques restent disponibles.

La clôture ne doit pas supprimer les informations ni empêcher de consulter ce qui a été réalisé.

Si le cabinet doit intervenir de nouveau, il faudra définir si cela nécessite une nouvelle mission ou une réouverture exceptionnelle de la mission existante.

# 15. Ce qui se passe lorsqu'une situation change

Il ne suffit pas de définir le parcours normal. Il faut aussi savoir comment Core Assist réagit lorsqu'un élément change.

Voici les principaux cas à prévoir.

| Situation | Réaction attendue de Core Assist |
|---|---|
| Le client apporte une nouvelle information | Elle est enregistrée et reliée aux besoins concernés. |
| Le périmètre change | Une nouvelle version du DSC est créée. Les analyses concernées sont signalées. |
| Un consultant est remplacé | Ses travaux restent conservés et le nouveau collaborateur reçoit les accès nécessaires. |
| Un consultant soumet un travail | Le chef de mission peut l'examiner. |
| Le chef de mission demande un complément | Le consultant peut reprendre le travail concerné. |
| Une nouvelle source contredit une analyse | L'analyse est signalée pour réexamen. |
| Un problème est reformulé | Le PSG conserve l'évolution et les liens avec les constats d'origine. |
| Une décision est annulée | L'ancienne décision reste dans l'historique avec son nouvel état. |
| Une source utilisée dans le rapport change | Le rapport n'est pas modifié automatiquement ; une vérification est nécessaire. |
| Le client demande une correction | Le cabinet examine la demande et prépare éventuellement une nouvelle version du rapport. |
| Une recommandation est refusée | Elle reste enregistrée avec son état et, si nécessaire, le motif du refus. |
| Une action est acceptée | Elle peut passer au suivi selon les modalités retenues par le cabinet. |

Il faudra définir précisément les personnes autorisées à effectuer ces opérations.

# 16. Les règles qui s'appliquent à tout le système

Il y a quelques règles importantes qui ne concernent pas un outil en particulier.

### A. Chaque utilisateur ne voit pas nécessairement les mêmes choses

| Utilisateur | Ce qu'il peut faire |
|---|---|
| DG | Accéder à toutes les missions et consulter les travaux soumis. |
| Manager | Gérer le portefeuille client et les missions relevant de ses responsabilités. |
| Chef de mission | Organiser les travaux, examiner les soumissions et demander des compléments. |
| Consultant | Consulter ses affectations, travailler, sauvegarder et soumettre ses travaux. |
| Expert | Intervenir sur les sujets et travaux qui lui sont confiés. |
| Client | Consulter les éléments qui lui sont communiqués, commenter et valider le rapport. |

Ces droits doivent être vérifiés à chaque opération, pas seulement à l'ouverture d'un écran.

### B. Les informations ne doivent pas être saisies plusieurs fois

Exemple : une information financière reçue est enregistrée une seule fois.

Elle peut ensuite être utilisée :
- pour répondre à un besoin du DIR ;
- pour compléter une contribution du SIG ;
- pour soutenir une analyse du D360 ;
- pour justifier un problème du PSG ;
- pour alimenter le rapport du DRD ;
- pour être retrouvée dans le DAP.

Chaque outil utilise la même information, mais conserve son propre rôle.

### C. Les anciennes versions doivent rester disponibles

Si le périmètre, une analyse ou un rapport change, Core Assist doit pouvoir retrouver les versions précédentes.

Il faut notamment savoir :
- qui a effectué la modification ;
- quand elle a été faite ;
- ce qui a changé ;
- pourquoi cela a changé, lorsque la justification est requise.

### D. Les outils ne doivent pas avancer uniquement parce qu'un autre outil a changé d'état

Exemple : le fait de valider le DSC peut permettre de préparer le DIR et le SIG.

Mais cela ne signifie pas que le DIR et le SIG sont terminés.

Autre exemple : la validation du rapport par le client ne clôture pas automatiquement la mission.

**Le système doit distinguer ce qui est rendu possible, ce qui est proposé et ce qui est réellement effectué par un utilisateur.**

## Mon analyse critique

Le principal risque que je vois est de construire Core Assist autour d'une succession de statuts : demande reçue, mission créée, outil démarré, outil terminé, mission clôturée.

Ce serait trop simpliste.

Dans notre fonctionnement, plusieurs choses peuvent se produire simultanément :
- le consultant collecte encore des informations ;
- un autre consultant analyse déjà les premiers résultats ;
- le chef de mission examine des travaux soumis ;
- le DG consulte l'avancement ;
- le LDC enregistre une décision ;
- le DRD commence à prendre forme.

Il serait donc incorrect de représenter toute la mission avec une seule barre de progression.
